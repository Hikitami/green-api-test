# Telegram-клиент на GREEN-API

Веб-приложение для личных текстовых сообщений в Telegram. Сделано на React и TypeScript в рамках тестового задания. Telegram выбран как одна из разрешённых альтернатив MAX.

В приложении два режима: подключение к GREEN-API и демо с вымышленными данными. Демо можно открыть без регистрации и токена. Оба режима доступны в готовой сборке.

## Запуск

Нужен Node.js 22.12 или новее. Для разработки использовал Node.js 24.

```bash
npm ci
npm run dev
```

По умолчанию адрес приложения — http://127.0.0.1:5173. Если порт занят, Vite покажет другой адрес в терминале.

Для проверки production-сборки:

```bash
npm run build
npm run preview
```

Preview доступен на http://127.0.0.1:4173. Для размещения на статическом хостинге достаточно содержимого `dist`. Переменные окружения и отдельный backend не требуются.

## Демо

На странице подключения нажмите **«Открыть демо без аккаунта»**. Поля формы заполнять не нужно.

В демо есть три диалога с историей. Можно отправить сообщение, получить автоматический ответ, посмотреть статусы доставки и создать новый чат по вымышленному номеру или `@username`.

В верхней панели доступны дополнительные сценарии:

- **Входящее сообщение** — добавить ответ в текущий чат.
- **Ошибка следующей отправки** — один раз отклонить отправку с тестовой ошибкой 429. Текст останется в переписке. Кнопка «Отправить повторно» перемещает сообщение в конец переписки с новым временем отправки, не создавая дубликат и не меняя черновик.
- **Выйти из демо** — очистить демосессию и вернуться к подключению.

Для проверки ненайденного пользователя введите `@not_found` при создании чата. Остальные корректные номера и имена в демо считаются существующими. Ответы заранее подготовлены, с настоящим Telegram они не связаны.

Данные хранятся в памяти вкладки. Демо не отправляет запросы к GREEN-API или Telegram. Его реализация находится в [src/app/demo](src/app/demo/README.md) и загружается отдельным модулем.

## Подключение к GREEN-API

Для обычного режима нужен авторизованный **инстанс Telegram** в [личном кабинете GREEN-API](https://console.green-api.com/). Токен бота от BotFather не подходит.

1. Создайте инстанс Telegram и авторизуйте его по QR-коду: Telegram → Настройки → Устройства → Подключить устройство.
2. В настройках инстанса оставьте `webhookUrl` пустым. Включите `incomingWebhook`, `outgoingWebhook` и `stateWebhook`. После сохранения настроек подождите около минуты.
3. В приложении введите `apiUrl`, `idInstance` и `apiTokenInstance` из кабинета. Адрес API нужно скопировать целиком, включая `https://`.
4. Нажмите **«Открыть сообщения»**, затем **«Новый чат»**. Укажите номер получателя с кодом страны или его `@username`.
5. Отправьте текст и ответьте из Telegram получателя. Ответ появится в том же диалоге.

При подключении приложение проверяет состояние инстанса и настройки получения сообщений. Если что-то не настроено, форма показывает ошибку. Настройки аккаунта приложение самостоятельно не меняет.

Поиск по номеру может не найти пользователя из-за приватности Telegram. В этом случае можно попробовать `@username`. Для определения идентификатора собеседника используется `CheckAccount`, отправка идёт через `SendMessage`.

Получение работает через последовательные вызовы `ReceiveNotification` и `DeleteNotification`. Не стоит одновременно запускать несколько клиентов для одной очереди: каждый из них будет забирать часть уведомлений.

## Возможности

- Несколько диалогов, поиск по списку и счётчики непрочитанных сообщений.
- Отдельный черновик для каждого чата.
- Отправка текста до 4096 символов: Enter отправляет, Shift+Enter добавляет строку.
- Состояния отправки, принятия в очередь, доставки, прочтения и ошибки.
- Повторное подключение к очереди после сетевого сбоя с увеличением задержки между попытками.
- Защита от повторных уведомлений и обработка статуса, который пришёл раньше ответа на отправку.
- Адаптивная компоновка, управление с клавиатуры и возврат фокуса после закрытия диалога.

## Архитектура

Использовал Feature-Sliced Design. Страницы собирают интерфейс из виджетов, пользовательские действия находятся в features, состояние диалогов и сессии — в entities.

```text
src/
  app/                  точка входа, стили, подключение демо
  pages/
    connect/            страница подключения
    messenger/          страница чата
  widgets/
    chat-sidebar/       список диалогов и поиск
    conversation/       переписка и поле ввода
  features/
    connect-instance/   подключение инстанса
    create-chat/        поиск получателя
    send-message/       отправка текста
    receive-messages/   обработка очереди уведомлений
  entities/
    session/            текущая сессия и её API-клиент
    chat/               диалоги, сообщения, черновики и статусы
  shared/
    api/                HTTP-клиент и проверка ответов
    lib/                нормализация номера и форматирование дат
    ui/                 общие компоненты
```

У слайсов есть публичные экспорты через `index.ts`. Зависимости направлены в нижние слои. ESLint проверяет направление импортов через алиас и запрещает обход публичного API.

Для общего состояния выбрал Zustand. Локальное состояние форм, поиска и модальных окон оставил в React. Отдельный кеш серверных запросов здесь не использовал: сообщения поступают из очереди событий и обновляют один стор.

Ответы API проверяются через Zod. HTTP-клиент не зависит от React, а цикл получения отделён от хука — его можно тестировать без браузера. Демо реализует тот же интерфейс клиента и использует обычные features отправки и получения.

Статусы сообщений привязаны к паре `chatId + idMessage`. Это не смешивает сообщения с одинаковыми ID из разных чатов. Если статус приходит до завершения `SendMessage`, он сохраняется до появления серверного ID у локального сообщения.

## Ограничения

История и черновики хранятся только до обновления страницы или выхода. История из Telegram не загружается. Уже подтверждённое уведомление нельзя повторно прочитать из очереди; сама переписка в Telegram при этом сохраняется.

Токен находится в памяти и не записывается в хранилища браузера или логи приложения. Он остаётся видимым в DevTools и сетевых запросах, как и любой секрет в клиентском приложении. Для сервиса с несколькими пользователями я вынес бы работу с токенами на backend.

После таймаута отправки результат может быть неизвестен: сервер мог принять сообщение до обрыва соединения. Поэтому автоматического повтора отправки нет. Приложение предлагает проверить Telegram и при необходимости вернуть текст в поле.

Реализованы личные текстовые сообщения. Файлы, звонки, редактирование и управление группами не входят в этот вариант. Нетекстовые события подтверждаются и пропускаются. Локальное прочтение чата не вызывает `ReadChat`, а статусы доставки в обычном режиме отображаются по уведомлениям GREEN-API.

## Проверки

```bash
npm run check          # линтер, unit-тесты, TypeScript и сборка
npm run format:check   # проверка форматирования
npx playwright install chromium
npm run test:e2e       # браузерные сценарии на desktop и mobile
```

Для тестов можно использовать установленный Chrome. Пример для PowerShell:

```powershell
$env:PLAYWRIGHT_CHANNEL='chrome'
npm run test:e2e
```

Для проверки уже запущенного приложения, в том числе production preview, задайте `E2E_BASE_URL`:

```powershell
$env:PLAYWRIGHT_CHANNEL='chrome'
$env:E2E_BASE_URL='http://127.0.0.1:4173'
npm run test:e2e
```

Unit-тесты покрывают нормализацию получателя, контракты HTTP-клиента, дедупликацию, порядок сообщений, черновики, гонки статусов и подтверждение очереди. Браузерные тесты проверяют подключение, отправку, ответы, ошибки, выход и работу без реальных данных в демо.

В тестах обычного режима запросы перехватываются Playwright и получают ответы в формате GREEN-API. Это проверяет интеграцию интерфейса с клиентом, но не заменяет обмен сообщениями через живой инстанс. Проверка с реальными учётными данными не проводилась.
